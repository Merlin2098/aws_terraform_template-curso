# Terraform Module Pattern

## When to use

- Packaging a reusable infrastructure component (S3 bucket, IAM role, Glue job)
- Standardizing how a resource is deployed across environments
- Refactoring inline resources into a reusable unit once the same block is copy-pasted twice

## Core idea

A module is a directory with three conventional files that together form its
contract: what it needs (`variables.tf`), what it builds (`main.tf`), and
what it exposes (`outputs.tf`). The most common module-design failure is
over-generalizing too early — building for hypothetical future callers before
a second real caller exists.

---

## Structure

```
modules/s3_data_lake/
├── variables.tf
├── main.tf
└── outputs.tf
```

```hcl
# variables.tf
variable "bucket_name" {
  description = "Name of the data lake bucket."
  type        = string
}

variable "enable_versioning" {
  description = "Enable S3 versioning. Off by default — see terraform_governance.md."
  type        = bool
  default     = false
}

variable "tags" {
  description = "Tags applied to all resources in this module."
  type        = map(string)
  default     = {}
}
```

```hcl
# main.tf
resource "aws_s3_bucket" "this" {
  bucket        = var.bucket_name
  force_destroy = true
  tags          = var.tags
}

resource "aws_s3_bucket_versioning" "this" {
  bucket = aws_s3_bucket.this.id
  versioning_configuration {
    status = var.enable_versioning ? "Enabled" : "Disabled"
  }
}
```

```hcl
# outputs.tf
output "bucket_name" {
  value       = aws_s3_bucket.this.id
  description = "Name of the created bucket."
}

output "bucket_arn" {
  value       = aws_s3_bucket.this.arn
  description = "ARN of the created bucket, for IAM policy scoping."
}
```

## Calling the module

```hcl
module "data_lake" {
  source      = "./modules/s3_data_lake"
  bucket_name = "${local.name_prefix}-data-lake"
  tags        = local.common_tags
}

# Downstream reference — no hardcoded bucket name
resource "aws_iam_policy" "read_data_lake" {
  policy = jsonencode({
    Statement = [{
      Effect   = "Allow"
      Action   = ["s3:GetObject"]
      Resource = "${module.data_lake.bucket_arn}/*"
    }]
  })
}
```

## Best practices

- Every external input is a variable — never hardcode a value a caller might
  need to change (bucket name, environment, region).
- Keep a module focused on a single responsibility (one S3 bucket pattern,
  one IAM role pattern) — a module that provisions unrelated resources is
  a sign it should split into two.
- Expose enable-flags, environment-aware defaults, and retention controls as
  variables when they materially affect cost or destroyability (e.g.
  `enable_versioning`, `log_retention_days`) — do not bury these as
  hardcoded values inside the module.
- Design so `terraform apply` → `terraform destroy` → `terraform apply`
  succeeds without manual cleanup. A module that leaves orphaned resources
  (e.g. a non-empty S3 bucket without `force_destroy`) fails this test.
- Declare supporting infrastructure the module's resource actually needs
  (a CloudWatch log group, for instance) explicitly inside the module,
  rather than relying on an autogenerated service-side default.

## Common mistakes

| Mistake | Why it hurts |
|---|---|
| Over-generalization | Adding configuration knobs for callers that don't exist yet adds complexity with no current benefit (Policy 008 — Prefer the Simplest Working Solution) |
| Tight coupling between modules | A module that reaches into another module's internal resources (instead of its declared outputs) breaks when the internal implementation changes |
| Orphan resources | Resources requiring manual console cleanup after `terraform destroy` (e.g. a non-empty bucket, an ECR repo with images) block clean teardown |
| Hardcoded names/ARNs inside a module | Prevents reuse across environments; every environment-specific value belongs in a variable |

---

## Avoid

- Hardcoding values a caller should be able to override
- A module handling more than one clearly separable responsibility
- Skipping outputs for values downstream resources or other modules will need
- Building configurability for a second use case that does not exist yet
